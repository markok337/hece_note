# 가계부 구현 계획

가계부 탭은 카드 결제 문자를 불러와 지출로 기록한다. 화면과 규칙 중 확정한 것은 [decisions.md의 "확정한 것: 가계부"](decisions.md)에 있다. 이 문서는 아직 만들지 않은 단계만 적는다.

**1단계(화면 시안)와 2단계(DB 연동)는 끝났고, 3단계의 DB 구조(문자함, 0005)도 만들었다.** 1단계는 모의 불러오기(지금은 없앴다), 표 화면, 가계부 안의 탭 4개(목록·결산·통계·설정), 목록 위 예산 요약, 결산의 이력 창, 12개월 분류 추이, 설정(예산 규칙, 분류 더하기·빼기)까지다. 아래 3~4단계는 순서대로 진행하고, 단계가 끝날 때마다 `decisions.md`의 해당 문장("1단계의 불러오기는 모의다" 등)을 현재 상태로 고친다.

## 2단계: DB 연동 (끝남)

실제 구현은 `0004_ledger.sql`, `repo.ts`, `store.svelte.ts`다. 아래는 설계 기록이다. 계획과 달라진 점: 예산·분류·카드는 `id` 기준 upsert라서 같은 범위·달을 다시 정하면 기존 행의 `id`를 재사용한다.

화면이 부르는 `ledger` 스토어의 메서드 모양은 그대로 두고, 저장만 Supabase로 바꾼다. 지출 항목, 카드, 분류 목록(`addCategory`·`removeCategory`), 예산 규칙(`setBudget`·`removeBudgetRule`)이 모두 대상이다. 가계부 안의 설정 탭은 같은 스토어를 쓰므로 화면 코드는 바뀌지 않는다.

- `supabase/migrations/0004_ledger.sql`: 테이블 다섯.
  - `ledger_entries`: id, spent_on(date), method(text), category(text, 1~10자. 분류를 설정에서 빼도 이력은 이름 그대로 남아야 하므로 목록을 가리키는 외래키나 check를 걸지 않는다), amount(integer, 0 제외, 절댓값 10억 이하), memo(100자 이하), sms_key(text, 없으면 null), created_at, user_id.
  - `ledger_categories`: id, name(1~10자), position(정렬 순서), created_at, user_id. `(user_id, name)` 유일. 행이 하나도 없으면 앱이 기본 분류 7가지를 채운다. 마지막 하나는 지우지 못하게 앱이 막는다.
  - `ledger_budget_rules`: id, scope(`base`/`from`/`only` check), month(date, 그 달 1일. `base`면 null), amount(integer, 1 이상), user_id. `base`는 사용자당 하나, `from`·`only`는 `(user_id, scope, month)` 유일. 한 달에 적용되는 값은 앱이 `budgetFor`로 "그 달만 → 그 달 이전 가장 최근 이후 규칙 → 기본값" 순서로 계산하므로 달마다 행을 채우지 않는다.
  - `ledger_cards`: id, name(20자 이하), sender(숫자 3~15자리), samples(0005에서 `{본문, 확정한 값}`의 jsonb 배열로 바뀜), created_at, user_id.
  - `(user_id, sms_key)`는 sms_key가 있을 때만 유일하게 한다. 같은 문자를 두 번 가져와도 DB가 막는다.
  - `(user_id, sender)`, `(user_id, name)`도 유일하다.
  - RLS는 냉장고와 같이 `owner_all`, Realtime 등록도 같다.
- `repo.ts`: 냉장고 `repo.ts`와 같은 모양(fetch·upsert·delete·subscribe).
- `store.svelte.ts`: `WriteQueue`로 낙관적 쓰기와 실시간 반영, 실패하면 서버 값으로 되돌림. `live`가 실제 연결 상태를 따라가므로 하단 표시가 "실시간"이 된다. 문자 처리 상태는 문자함(아래)에 저장해 기기끼리 맞춘다.
- 테스트: 냉장고 스토어 테스트와 같은 방식(repo를 mock), `schema-parity.test.ts`에 분류 목록과 check 일치 검증 추가.
- 사용자가 할 일: Supabase SQL Editor에서 0004를 실행한다(`docs/setup.md`의 방식). 실행하기 전에는 가계부 탭이 "불러오기 실패"를 띄운다.

## 문자함 (DB 구조는 끝남, 0005)

용량을 적게 쓰려고 기간을 30일로 고정하고 그 기간의 문자를 전부 쌓는다. 구현은 `0005_ledger_sms.sql`, `repo.ts`, `store.svelte.ts`의 `receiveSms`·`pendingSms`·`ignoreSms`·`resetIgnored`다. 확정한 규칙은 [decisions.md의 "문자 불러오기와 문자함"](decisions.md)에 있다.

- `ledger_sms`: id, sms_key(같은 문자를 두 번 쌓지 않는 식별값, `(user_id, sms_key)` 유일), sender, received_at, body(2000자 이하), status(`pending`/`done`/`ignored`), user_id. 새 문자는 이미 있는 `sms_key`를 건드리지 않고 쌓아서 완료·무시 상태가 되돌아가지 않는다.
- 30일이 지난 줄은 앱이 문자를 불러올 때 지운다(서버 예약 작업 없음). 완료한 항목은 지워지지 않는다. 항목의 `sms_key`와 중복 방지 인덱스가 그대로라 같은 문자를 두 번 항목으로 만들 수 없다.
- 0004의 `ledger_dismissed`는 `ignored` 상태가 대신하므로 0005에서 지운다.
- `ledger_cards.samples`는 `{body, values}` 배열(카드당 20개까지)이다. `values`는 사용자가 그 문자에서 확정한 날짜·금액·가맹점이고, 규칙은 앱이 견본에서 계산한다. 같은 모양이 이미 있으면 견본을 늘리지 않는다.
- 취소 문자는 원래 결제와 짝을 짓지 않고 음수 금액의 별개 항목으로 둔다.

## 3단계: 문자 규칙 (견본으로 읽는 법 정하기)

카드사 문자 모양을 코드에 박지 않고, 카드를 등록할 때 넣은 견본에서 앱이 읽는 규칙을 만든다.

- `sms-guess.ts`(순수 함수, 만들었다): 문자 한 건에서 금액, 가맹점, 날짜, 승인/취소를 뽑는다. 먼저 견본의 틀에 맞춰 보고, 맞는 틀이 없으면 아는 모양으로 읽는다.
- (양식 화면과 견본 저장은 만들었다. 아래는 이를 바탕으로 **견본이 쌓인 뒤** 자동 채움 규칙을 만드는 일이다.) 문자함에서 문자를 누르면 추가 양식이 열리고, 문자에서 뽑은 값이 먼저 채워지며, 못 뽑은 값은 비어 있다. 분류는 사용자가 고르고, 안 고르면 추가할 수 없다. 앱은 금액(`숫자원`), 날짜(`11/13`, `2026.11.13`) 같은 흔한 모양을 먼저 짐작한다. 사용자가 고쳐 채운 결과가 기존 규칙으로 읽지 못한 새 모양이면 견본(`ledger_cards.samples`)으로 쌓고, 문자에 글자 그대로 있는 값만 규칙이 된다. 자동 채움이 틀렸거나 비었을 때만 견본을 늘린다.
- 한 번호에 견본을 여러 개 둘 수 있다(결제·취소·해외결제 등). 규칙에 맞지 않는 문자는 지출로 만들지 않고 "읽지 못한 문자"로 보낸다. 모양이 바뀐 문자가 조용히 빠지거나 엉뚱한 금액으로 들어가지 않게 하려는 것이다. 읽지 못한 문자는 문자함에 처리 필요로 남고, 사용자가 양식을 채워 추가하면 견본이 늘어난다.
- 문자에 연도가 없으면 문자를 받은 시각의 연도를 쓴다. 연말·연초 경계(12월 문자를 1월에 읽는 경우)를 테스트한다.
- 취소는 음수 금액 항목으로 들어간다.
- 테스트: 견본(가짜 문자) 몇 종류로 결제·취소·읽지 못함·날짜 모양·금액 쉼표·연도 경계. 실제 카드번호·이름은 테스트에 넣지 않는다.

## 4단계: 안드로이드 앱(APK)과 실제 문자 읽기

(만들었다. 빌드와 설치는 [setup.md 8절](setup.md), 확정한 규칙은 [decisions.md의 "안드로이드 앱"](decisions.md). 아래는 설계 기록이고, 남은 것은 실기기 확인이다.)

- **껍데기 APK**: Capacitor로 만들고, 앱이 배포 주소(`https://markok337.github.io/hece_note/`)를 열게 한다(`server.url`). 화면 코드는 APK에 넣지 않으므로 화면 업데이트는 배포만으로 끝난다. 폴드8, S26에 직접 설치한다. 플레이스토어에는 올리지 않는다(문자 읽기 권한을 정책상 허용하지 않는다).
- **문자 읽기**: 안드로이드 `READ_SMS` 권한으로 문자함을 조회하되, 등록한 발신번호의 문자만 조회한다. 직접 만든 작은 플러그인(`SmsInbox`)으로 정했다.
- **권한 안내**: 직접 설치한 앱은 안드로이드 13 이후 문자 권한이 막혀 있다. 앱 정보에서 "제한된 설정 허용"을 켜고 문자 권한을 줘야 한다. 이 절차를 `docs/setup.md`에 적는다.
- **불러오기 버튼**: `sms-reader.ts`의 `readSms`가 플러그인을 불러 문자를 문자함 모양으로 돌려준다. APK 안에서 열렸는지 확인해, 아닐 때(PC·노트북의 PWA)는 이유를 알린다. 어느 기기에서 열어도 코드는 하나다.
- **읽는 범위**: 최근 30일(문자함 보관 기간)이다. 이미 쌓인 문자는 식별값으로 건너뛴다.
- **자동으로 불러오지 않는다.** 사용자가 버튼을 눌렀을 때만 읽는다.
- 확인: 폴드8·S26 실기기에서 권한 허용 → 불러오기 → 확인 창 → 추가 → PC 브라우저에 같은 항목이 뜨는지, 같은 문자를 다시 불러오면 건너뛰는지 본다.
